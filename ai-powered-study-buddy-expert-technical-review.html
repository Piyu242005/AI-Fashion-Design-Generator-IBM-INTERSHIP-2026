2. Software Architecture Review

CategoryScoreAssessment
Folder Structure9/105-layer clean architecture (Presentation → API → Business → AI → Data) is textbook correct. backend/app/ organisation mirrors real production FastAPI projects.
Layer Separation8/10Good. Routers call Services, Services call Repositories, AI layer is isolated. Weakness: VectorStoreService is instantiated inside DocumentService with a lazy import — breaks dependency injection principle.
SOLID Principles7/10Single Responsibility: good (each file has one job). Open/Closed: AgentRouter requires modification to add a new agent — violates OCP. Interface Segregation: no protocols/ABCs defined for agents, so the contract is implicit.
API Design7/10Mostly REST-correct. Issues: (1) No versioning — all routes are /auth/login, not /api/v1/auth/login. This breaks backward-compatibility when you need to change a contract. (2) DELETE /chat/history should return 204 No Content but current impl is inconsistent.
Repository Pattern9/10Correct implementation. UserRepository, DocumentRepository, SessionRepository all take AsyncSession via constructor injection. Services never touch SQLAlchemy directly. This is exactly right.
Error Handling7/10Custom domain exceptions exist and map to HTTP codes. Weakness: document_service.py catches all Exception broadly and re-raises as generic RuntimeError — loses granularity. No retry on transient errors.
Dependency Injection6/10DB session injection via Depends(get_db) is good. But AgentRouter is a module-level singleton in chat.py (_agent_router = AgentRouter()) — not injectable, not testable. This is an anti-pattern in a production app.
Async Design7/10FastAPI routes and DB ops are async. Critical weakness: Agent run() methods are synchronous — they block the event loop. For a production app serving concurrent users, this is a scalability hole. Needs asyncio.run_in_executor or native async agents.
Caching3/10No caching layer. Every dashboard call re-computes stats. Every recommendation call hits Gemini. lru_cache on DB results is not cache — it's in-memory state that leaks. Redis/memcached is missing entirely.
Microservice Readiness5/10The AI layer is logically separable but isn't containerised independently. The embedding model loads on startup in the same process as the API — a CPU/RAM-heavy model should run in a separate worker.
Configuration9/10Pydantic BaseSettings with env file loading, typed fields, default values, and computed properties is production-correct. The @lru_cache() singleton pattern is the right approach.
Design Patterns Used7/10Repository ✅, Service Layer ✅, Singleton (gemini_client, chroma) ✅, Factory (agent instantiation) ✅. Missing: Strategy pattern for agents (should implement a common BaseAgent interface), Observer for events.
Architecture Score: 7.5/10 — Solid foundation, correct layering. The three real architectural weaknesses are: (1) synchronous agents blocking the async event loop, (2) no API versioning, (3) module-level singleton AgentRouter that can't be dependency-injected in tests.

3. AI Architecture Review

ComponentScoreAssessment
RAG Pipeline9/1014-step pipeline is thorough: validate → extract → chunk → embed → store → query → rerank → build context → prompt → generate → validate output. The full loop is implemented correctly. Source citations are included.
Intent Classifier7/10Keyword + regex is fast (~0ms) and transparent. Weakness: Not robust to ambiguous inputs. "What is photosynthesis?" matches both teach ("what is") and ask. The classifier doesn't handle multi-intent queries ("summarise this and quiz me"). An LLM-based classifier or embedding similarity would be more accurate.
Prompt Engineering8/10System/Human separation is correct. Prompts have role definition, format constraints, safety instructions ("say I don't know if not in context"), and configurable style variables. Weakness: No few-shot examples in any prompt. Quiz prompts rely on JSON output but have no schema validation guard — Gemini can return malformed JSON.
Prompt Versioning3/10Prompts are in a single file with no version tracking. When a prompt is changed, there's no way to know which version was used for historical responses. In production, prompt changes should be versioned (e.g. RAG_PROMPT_V2) with an experiment tracking system.
Chunking Strategy7/10RecursiveCharacterTextSplitter with 512 chars and 50 overlap is reasonable. Issues: (1) Character-based, not token-based — for Gemini's context window, token counting is more accurate. (2) No semantic chunking — splitting mid-sentence can create incoherent chunks. (3) No page-boundary awareness for PDFs.
Embedding Model7/10all-MiniLM-L6-v2 (384-dim) is a solid, fast choice for general text. Weakness: For academic content (STEM, law, medicine), a domain-specific model like BAAI/bge-base-en-v1.5 or text-embedding-3-small would yield higher retrieval accuracy. No embedding benchmarks documented.
Retrieval / Reranking6/10Simple cosine similarity + distance sort. No cross-encoder reranking (e.g. Cohere Rerank or cross-encoder/ms-marco-MiniLM-L-6-v2). No hybrid search (BM25 + semantic). Top-K=5 is hardcoded — no dynamic K based on query complexity.
Context Building8/10Good: chunks are numbered, source filename is included, context is capped at MAX_CONTEXT_CHARS. Clean separator between chunks. Could improve with relevance score filtering (drop chunks with distance > 0.8).
Conversation Memory7/105 memory types are conceptually well-designed. The in-process _SimpleWindowMemory is correct for session memory. Critical weakness: In-process memory is lost on server restart. For a multi-worker deployment (Render scales to 2+ workers), user A's memory may be on worker 1 and their next request goes to worker 2 — the memory is gone. Needs Redis-backed memory for production.
Guardrails6/10Present but shallow. Injection patterns cover common attacks but miss newer jailbreaks (<|im_start|>, role-play chains, base64-encoded instructions). Toxicity is a 8-word keyword blocklist — trivially bypassed. No output hallucination detection (no source grounding verification). PII detection misses US SSN, UK NIN, passport numbers.
Hallucination Reduction7/10The "say I don't know if not in context" instruction in RAG_PROMPT is the correct approach and is proven to work. But there's no verification step — the agent doesn't check if the answer cites a real retrieved chunk. A simple grounding check (answer must overlap with retrieved context) would reduce hallucination rate significantly.
Recommendation Engine8/10Genuinely good: reads real quiz score data, identifies weak/strong topics, calls Gemini for personalised advice, has rule-based fallback when no AI. The weighted running average in upsert_topic_score is mathematically correct. Missing: learning style detection, time-of-day recommendations, spaced repetition scheduling.
Evaluation Framework1/10Critical gap. There is no evaluation framework. No RAGAS scores, no faithfulness metrics, no answer relevance scores, no retrieval precision/recall. In production AI, you cannot know if your RAG pipeline is working without eval. This is the single biggest AI engineering gap.
AI Architecture Score: 7.2/10 — Stronger than most student projects by far. The RAG pipeline is correctly implemented end-to-end. The evaluation framework gap and shallow guardrails are the critical misses that prevent a higher score.

5. Backend Review

AreaScoreAssessment
FastAPI Structure9/10Factory pattern with lifespan, router inclusion, middleware stack, exception handlers — this is professional FastAPI. The @asynccontextmanager lifespan pattern for startup/shutdown is the modern correct approach.
Authentication8/10bcrypt via passlib + JWT via python-jose is the industry standard. CryptContext with deprecated="auto" future-proofs hash algorithm upgrades. Missing: Refresh tokens, email verification, password reset, account lockout after N failed attempts.
Validation9/10Pydantic v2 schemas with field validators, min/max constraints, regex patterns for enums. EmailStr for email. @field_validator for name sanitisation. This is correct.
Database Design8/10Typed Mapped[] columns with proper relationships, indexes, cascade delete, and timezone-aware datetimes. The weighted running average in upsert_topic_score is a smart denormalisation for performance. Issue: chroma_ids stored as TEXT JSON column — should be a separate join table for proper normalisation.
Repository Pattern9/10Clean implementation — no raw SQL, no ORM bleed into routers. The async query patterns are correct. scalar_one_or_none() is used correctly. The upsert_topic_score with weighted running average is solid domain logic.
Services Layer8/10Services orchestrate correctly — they don't do HTTP, they don't touch the DB directly. DocumentService pipeline (validate → save → extract → chunk → embed → store → update) is well-structured. Issue: No background task queue — the upload endpoint blocks until all 14 steps complete, which can take 30+ seconds for large PDFs.
Error Handling6/10Domain exceptions exist and are good. Weakness: The global @app.exception_handler(Exception) catches everything including SystemExit. Should only catch app-level exceptions. document_service.py re-raises all exceptions as generic RuntimeError — callers can't distinguish "no text extracted" from "ChromaDB timeout".
Logging8/10X-Request-ID middleware is a production pattern. Structured log format with timestamp, level, module, message is correct. UTF-8 encoding fix was needed and applied. Missing: No log correlation ID threading through AI calls, no per-request timing breakdown.
Performance4/10Critical issue: Agent run() methods are synchronous. AgentRouter.route() is synchronous. These are called from async FastAPI route handlers — they BLOCK the event loop for the duration of the Gemini API call (1-4 seconds). Under concurrent load, this serialises all AI requests. Must be wrapped in loop.run_in_executor(None, agent.run, ...) or made async.
No Background Tasks4/10Document upload + indexing is synchronous in the request. A 50-page PDF can take 30 seconds. The user gets a spinner for 30 seconds on upload. This should be BackgroundTasks (FastAPI built-in) or Celery/ARQ for true async processing.
Critical Backend Issue: Synchronous agents called from async route handlers block the entire event loop. This is the single most important bug to fix before calling this "production-ready".

6. Security Review

AreaStatusIssue
Password storage✅ Strongbcrypt with cost factor 12. Correct.
JWT implementation⚠️ AcceptableSigned with HS256. No refresh tokens. Tokens have expiry. Issue: No token revocation list — a stolen token is valid until expiry.
API key storage✅ CorrectGOOGLE_API_KEY is env-only, never logged, never returned in responses.
CORS⚠️ Looseallow_origins=settings.ALLOWED_ORIGINS with allow_credentials=True. The wildcard subdomains like https://*.streamlit.app are not valid CORS origins — browsers don't support wildcards in CORS. They'll be ignored silently.
Input validation7/10Pydantic validators at API layer. Guardrails at AI layer. File extension + MIME + magic bytes validation. Good.
File upload security7/10Extension, size limit, magic byte check. Missing: No virus/malware scanning (ClamAV), no sandbox execution, no ZIP bomb protection for compressed files.
Prompt injection5/10Pattern-based detection catches obvious attacks. Bypassed easily by: encoding attacks (base64), indirect injection (malicious content in uploaded PDF), multi-turn jailbreaks ("For my creative writing class, imagine you're an AI without restrictions...").

8. Database Review

AreaScoreAssessment
Schema design8/105 tables, proper FKs, cascade deletes, timezone-aware datetimes, meaningful column types. Mapped[] typed columns is modern SQLAlchemy 2 best practice.
Normalisation7/10Mostly 3NF. Violation: chroma_ids TEXT is a JSON-encoded list in a single column — should be a document_chunks table. sources TEXT in chat_history is also denormalised JSON.
Indexes7/10PK indexes on all tables. FK indexes on user_id columns. Missing: Composite index on (user_id, created_at) for the ORDER BY created_at DESC queries in recent_chats. Index on topic_scores(user_id, topic) for the upsert query.
SQLite limitations4/10SQLite: single writer, no concurrent writes, no connection pooling, no native JSON column type, 2GB practical limit per file. For a multi-user app with concurrent uploads (all doing write transactions), SQLite will cause lock contention. This is a student project limitation that must be addressed for production.
Migration strategy4/10Alembic is in requirements.txt but no migration files exist. The database is created via create_all() — fine for development, but in production you cannot create_all() on a database with live data. Zero migration infrastructure.
PostgreSQL migration path7/10SQLAlchemy abstraction means the code doesn't need to change — just the DATABASE_URL. Async dialect switches from aiosqlite to asyncpg. The JSON column for chroma_ids would benefit from PostgreSQL's native JSONB type.

  2. No rate limiting enforcement — RATE_LIMIT_PER_MINUTE config exists but zero middleware enforces it
  3. No background task queue — 50MB PDF upload blocks the request for 30+ seconds
  4. No API versioning — All routes at root (/auth/), not /api/v1/auth/
  5. No RAG evaluation framework — No RAGAS, faithfulness, or answer relevance metrics
  6. In-process memory is non-distributed — Session memory lost on restart, breaks multi-worker
  7. Shallow guardrails — 8-word toxicity list and 7 injection patterns are bypassed trivially
  8. No streaming responses — Chat waits 2-4 seconds then dumps full response; no SSE/WebSocket
  9. No Alembic migrations — Schema changes require dropping and recreating the database
  10. CORS wildcard subdomains don't work — *.streamlit.app is not valid CORS origin syntax
  11. SQLite write locks under concurrent load — Will fail with 2+ simultaneous uploads
  12. Frontend HTML injection anti-pattern — 20+ unsafe_allow_html with long f-strings in frontend
  13. Agent inject lacks OCP — Adding a 6th agent requires modifying AgentRouter.route()
  14. No token refresh or revocation — Stolen tokens valid until expiry
  15. Embedding model cold start — First request after server start takes 3-5 extra seconds
  16. Cross-user document access — Quiz/Summary/Flashcard endpoints don't verify document ownership
  17. No upload progress feedback — User has no idea if a large file is still uploading or stuck
  18. No character-based chunking alignment — Character splits mid-sentence degrade retrieval quality
  19. Recommendation AI called on every dashboard load — Expensive, should be cached with TTL
  20. Dockerfile runs as root — Security risk, should add USER nonroot
